# A3 超节点内直接访存竞争实验设置

版本：v1.0  
日期：2026 年 10 月 16 日  
状态：实验方案，尚无实测结论

## 1 实验目标与范围

本实验研究 A3 超节点内，后台直接读取对关键读取尾时延的影响，并评估限制后台在途数量和调整请求准入顺序的效果。先在同一服务器内选择两个可直接互访的 NPU，再扩展到同一超节点内的跨服务器设备，分别测试 SDMA 和 MTE 路径。

第一轮优先回答三个问题：

1. **竞争是否存在**：后台读取运行时，关键读取的 p95、p99 是否稳定上升？
2. **积压是否有害**：后台吞吐趋于稳定后，继续增加后台在途上限是否仍会恶化关键读取尾时延？
3. **限流是否有效**：在固定工作量下，降低后台在途上限或调整准入顺序，能否改善关键读取时延，代价是多少？

本实验提供共享访存资源协调是否有优化空间的证据。仅凭时延和吞吐变化，不能认定硬件请求槽、返回缓冲或其他特定资源耗尽，也不能直接证明 CMU 的硬件实现收益。

## 2 实验角色与访问方向

| 对象 | 角色与配置 |
| --- | --- |
| D0 | 请求端，同时发起关键读取 H 和后台读取 P |
| D1 | 数据源，在 HBM 中准备互不重叠的 H 源区和 P 源区 |
| H | 关键读取，每次 64 KiB，最多保留一笔未完成请求 |
| P | 后台读取，请求大小分别为 4 KiB、64 KiB、1 MiB |
| 访问方向 | H、P 均由 D0 从 D1 读取数据 |
| D0 目标缓冲 | H、P 分开分配；P 的未完成请求使用独立目标槽位，避免写入冲突 |
| K | P 的逻辑在途上限，初始扫描 1、2、4、8、16、32 |

D0、D1 是实验角色，不代表物理设备编号 0、1。应先根据实际拓扑选择设备，并记录逻辑设备 ID、rank、物理端点和所属服务器的映射关系。

**逻辑在途请求**定义为已被所选后端接受、但尚未确认完成的一个应用层读取工作单元。K 不包含尚未准入的软件待提交队列，也不等于硬件事务数或硬件队列深度。应同时记录待提交数、实际在途数和完成数。

对于 MTE，必须明确一个逻辑 P 对应一个 kernel、kernel 内的一段 copy，还是一个工作描述符；对于 SDMA，也必须明确请求与拷贝调用、批次及完成事件的映射。不同后端分别解释 K，不能将相同 K 视为相同硬件负载。

## 3 环境配置与运行前检查

### 3.1 环境记录

| 类别 | 必须记录的信息 |
| --- | --- |
| 硬件 | 服务器型号、NPU 型号与数量、超节点标识、D0/D1 所属服务器 |
| 设备映射 | 进程可见逻辑 ID、rank、物理 ID 或可获取的硬件端点标识 |
| 拓扑 | 同机或跨机、实际互连关系、直接访问能力及验证方法 |
| 软件 | OS、驱动、固件、CANN、运行时、编译器、MemFabric 版本及 commit |
| 后端 | SDMA/MTE、实际调用接口、配置参数、异步能力与完成判定方式 |
| 提交配置 | 进程/线程数、CPU 亲和性、stream、优先级、锁和同步机制 |
| MTE 配置 | kernel 名称、block 数、每 block 工作量、buffer/pipeline 配置 |
| 运行状态 | 其他作业、设备利用率、温度、频率、功耗及相关限制配置 |
| 内存配置 | H/P 源区和目标区大小、对齐、工作集、地址种子、缓存相关设置 |

### 3.2 路径验证

正式计时前完成以下检查，并保存日志：

1. D0 可通过指定后端读取 D1 HBM；校验内容与预期一致。
2. 确认所用接口的实际传输路径，检查是否存在主机中转、后端回退或隐式数据复制。不能确认时，将路径标记为“待确认”，不用于同路径因果比较。
3. 通过异步提交与完成事件，或等价的时间线证据，确认 H 和 P 确实可以重叠执行。
4. 检查每个请求的完成语义，确保“完成”表示目标数据已按接口约定可用，而非仅表示请求已入队。
5. 初始化、内存分配、注册、映射、编译及连接建立均在计时区间外完成。
6. 使用独立预检或抽样校验验证正确性；校验开销不计入正常性能样本。测试结束后再次校验结果。

若接口是同步接口或实现始终串行执行，不能将其作为并发访存竞争实验；应先解决并发能力，或单独标注为串行对照。

## 4 统一负载设置

### 4.1 固定参数与扫描参数

| 参数 | 首轮设置 | 控制要求 |
| --- | --- | --- |
| H 请求大小 | 64 KiB | 全部首轮实验固定 |
| H 最大在途数 | 1 | 上一笔完成后才能提交下一笔 |
| P 请求大小 | 4 KiB、64 KiB、1 MiB | 分开测试 |
| P 在途上限 K | 1、2、4、8、16、32 | 出现稳定趋势后再决定是否扩大 |
| 后端 | SDMA、MTE | 分开建立基线、测试和分析 |
| 地址模式 | 连续、离散 | 分开测试并固定种子 |
| 拓扑 | 先同机，后跨服务器 | 跨机仍在同一 A3 超节点内 |
| 数据方向 | D0 读取 D1 | H、P 方向一致 |

容量统一使用二进制单位：1 KiB = 1024 B，1 MiB = 1024 KiB，1 GiB = 1024 MiB。吞吐统一报告 GiB/s，并保留原始字节数与时间。

### 4.2 地址与工作集

H、P 的源区和目标区互不重叠。连续模式在各自工作集内顺序访问并循环；离散模式在满足后端对齐要求的偏移集合中使用固定随机种子生成访问序列。离散访问不得越界。

H 即使每次大小固定，也应在独立工作集内轮换地址，避免反复读取同一小块数据导致结果主要反映缓存命中。记录实际工作集大小、访问步长、地址重复周期和可控的缓存设置；若缓存状态不可控，应说明限制，不直接宣称测得的是纯远端 HBM 时延。

大块与小块实验使用相同逻辑数据集和确定性遍历规则。请求划分不同会改变事务拆分、局部性及控制开销，因此请求大小效应需要结合地址模式解释。

### 4.3 H 发起方式

首轮采用闭环方式：H 完成后按固定间隔 G 发起下一笔，建议初值 G = 0，并在每个配置中保持一致。P 使用独立提交逻辑，不能等待 H 完成才允许推进。

闭环测量反映“最多一笔 H 在途”条件下的请求时延；H 变慢时，其实际到达率也会下降。因此必须记录 H 完成率，不能将结果直接推广为固定外部到达率下的排队时延。

若后续引入周期到达或真实业务轨迹，需单独定义软件排队、延迟提交及丢弃规则，并另列实验。

### 4.4 重复与采样

以下为建议起始值，应在预试验后统一冻结，并非硬件规格：

- 每个配置预热至少 5 s，确认完成率和吞吐无明显持续漂移后开始采样。
- 每轮正式采样至少 30 s，且获得至少 100,000 个 H 完成样本；两项均满足后结束。若受运行预算限制未达到，标记实际样本量并说明 p99 的统计限制。
- 每个配置至少独立重复 5 轮，打乱配置顺序，避免温度或系统状态随时间变化造成顺序偏差。
- 每批混合负载测试前后各运行一次同后端、同地址模式的 H 基线，检查漂移。
- 固定工作量实验以任务全部完成为结束条件，保持每个策略的 H/P 数量及字节量一致。

主测试使用轻量时间戳。详细 profiling 单独重复采集，并记录其额外开销，不混入正常性能统计。

## 5 四组核心实验

### 5.1 E1 关键读取空载基线

**目的**：测量无 P 条件下 H 的延迟分布和提交开销。

**步骤**：

1. 分别选择 SDMA 和 MTE 后端。
2. 分别运行连续与离散地址模式，只运行 H。
3. 按统一预热、采样与重复规则记录数据。
4. 保存对应后端及地址模式的 p50、p95、p99、提交耗时和 H 完成率。

E1 共 2 个后端 × 2 种地址模式 = 4 个配置，不含重复轮次。不支持的后端或路径记录为不支持，不以其他后端替代。

### 5.2 E2 扫描后台在途上限

**目的**：观察 K 增大时 H 的尾时延和 P 的实际吞吐如何变化。

**步骤**：

1. 固定后端、地址模式、H 大小、H 发起规则和工作集。
2. 选择一种 P 大小，依次测试 K = 1、2、4、8、16、32；实际运行顺序随机化。
3. P 达到稳定状态后，开始 H/P 共同采样；P 在采样窗口内持续运行。
4. 每有 P 完成才释放逻辑在途额度，并在额度允许时补充 P。
5. 对其他 P 大小重复上述步骤，最后切换地址模式及后端。

完整 E2 为 2 个后端 × 2 种地址模式 × 3 种 P 大小 × 6 个 K = 72 个配置。若先做预试验，可从连续地址、P = 64 KiB 开始，再补齐矩阵。

**记录与判断**：绘制 H p99 随 K 变化曲线和 P 吞吐随 K 变化曲线，同时检查实际在途分布。若吞吐增幅已小于重复实验波动，而 H p99 仍持续上升，可认为继续增加逻辑积压的收益有限。不能据此单独定位硬件资源。

### 5.3 E3 相同后台总字节量的大块与小块对比

**目的**：区分后台字节流量与请求数量、地址模式、控制开销的影响。

**配置**：主要比较 P = 4 KiB 与 P = 1 MiB；可增加 64 KiB 作为中间点。固定同一后台数据集、累计读取字节数 B、H 设置、后端和地址模式。B 取 1 MiB 的整数倍，建议从 8 GiB 开始，根据预试验扩大到足以覆盖稳定测量窗口的规模。

**步骤**：

1. 先独立测量各 P 大小可持续达到的完成带宽。
2. 选择两种请求大小均可实现的共同目标发起字节率 R，以字节预算控制平均发起负载。记录限速窗口或突发预算，防止相同均值掩盖不同突发程度。
3. 在相同目标 R、相同累计 B 下运行 H＋P。不同 P 大小的目标请求率为 R / P_size。
4. 在途上限应允许达到目标 R；记录 K 和实际在途数。若为匹配 R 调整了 K，应明确列出，避免把差异全部归因于请求大小。
5. 同时报告实际提交字节率、实际完成带宽和有效请求率。只在达到相近实际负载的区间内作主要比较。
6. H 在 P 活跃期间持续运行，只在两者共同活跃的稳定窗口统计混合负载时延；窗口定义在各组保持一致。

可补充一组“相同 B、相同 K、不限发起率”的测试，展示饱和压力下的整体差异，但必须与匹配发起字节率的主实验分开分析。

**解释边界**：若在可比的实际字节率下，小块 P 对 H 的影响仍更大，说明请求数量、事务拆分、局部性或控制开销等因素值得继续分析。SDMA 和 MTE 分别判断，不假设同大小应用请求对应同样硬件事务。

### 5.4 E4 固定工作量下的准入策略对比

**目的**：量化尾时延改善、后台吞吐损失及全部任务完成时间之间的关系。

从 E2 选择干扰稳定且可以重复的配置，固定 H/P 请求序列、请求数量、后台总字节数、地址种子及后端。固定工作量测试可与持续压力测试采用不同终止规则，但策略间必须一致。

| 策略 | 设置 | 主要比较 |
| --- | --- | --- |
| S0 高在途基准 | 使用 E2 中出现明显干扰的 K_high | 确定未限流时的代价 |
| S1 降低在途上限 | 使用预先选定的 K_low，其他规则与 S0 一致 | 单独评估 K 限制 |
| S2 H 到达时优先准入 | K 与 S0 相同；H 就绪时暂停新 P 提交，H 被接受后恢复 | 单独评估提交顺序调整 |

S2 必须定义“到达”为 H 被标记为就绪的时刻；通过提交协调机制，使该标记之后的新 P 暂停，直到 H 已成功提交。已经提交的 P 不取消、不抢占、不排空。此策略仅调整后续准入顺序，不保证 H 立即获得硬件服务。

如需验证“暂停 P 直到 H 完成”或“先排空 P 再提交 H”，应另建策略编号；它们的暂停范围及等待成本不同，不能与 S2 混为一组。

每轮从共同起始点启动固定 H/P 工作量，直至两类任务全部完成。分别报告共同活跃窗口的性能、全程性能及共同活跃样本占比，防止一类任务提前结束后的空载样本稀释干扰。

## 6 测量指标与时间边界

### 6.1 H 时间戳

每笔 H 至少记录以下同一主机单调时钟下的时间点：

| 时间点 | 含义 |
| --- | --- |
| t_ready | H 按负载规则就绪，开始计入策略等待 |
| t_call | 开始调用后端提交接口 |
| t_return | 提交接口返回 |
| t_done | 按后端完成语义观察到完成 |

- 软件准入等待：t_call − t_ready。
- 提交调用耗时：t_return − t_call。
- 提交到可观测完成时延：t_done − t_call。
- 端到端时延：t_done − t_ready，**作为策略比较的主要 H 指标**。

提交到可观测完成时延包含软件提交、设备排队、执行及完成检测开销，不称为纯硬件访存时延。不要把提交返回时刻当作设备服务开始时刻；同步调用也不能仅据 t_done − t_return 判断设备耗时。

若运行时提供可靠的设备侧 event 或 profiling 时间戳，额外记录入队、kernel 启动、kernel 结束和内部读取区间。不同时间域只有在完成校准后才可相减。记录计时分辨率、完成轮询周期、事件粒度及时间戳采集开销。

### 6.2 统计与派生指标

| 指标 | 计算口径 |
| --- | --- |
| H 时延分位数 | 对端到端时延及提交到完成时延分别报告 p50、p95、p99，注明样本量 |
| H 提交耗时 | 报告均值及 p50、p95、p99，用于识别软件提交阻塞 |
| P 实际吞吐 | 测量窗口内确认完成的有效 P 字节数 / 窗口时长 |
| P 请求率 | 窗口内完成的 P 逻辑请求数 / 窗口时长 |
| P 实际在途 | 记录时间加权均值、最大值，以及条件允许时的分布 |
| H 尾时延放大 | 混合负载 H p99 / 匹配 E1 的 H p99 |
| H p99 改善率 | (S0 的 H p99 − 策略 H p99) / S0 的 H p99 |
| P 吞吐损失率 | (S0 的 P 吞吐 − 策略 P 吞吐) / S0 的 P 吞吐 |
| 全部任务完成时间 | 最后一笔 H/P 完成时刻 − 共同起始时刻 |
| 完成时间变化率 | (策略完成时间 − S0 完成时间) / S0 完成时间 |

固定工作量实验额外报告 P 总字节数 / P 活跃时长，以及 P 总字节数 / 全部任务完成时间，两者分别命名，不混用。吞吐为完成吞吐，不能用提交字节量替代。

分位数使用固定算法，例如 nearest-rank；所有配置一致。每轮分别计算分位数，汇总各轮结果及其范围，保留原始样本。样本量充足时可进一步给出置信区间；不要仅报告某一轮的最优结果。

## 7 两类后端的干扰排查

### 7.1 SDMA

重点排除 H 被软件锁、同一 stream 的顺序执行或同步接口串行阻塞的情况。H/P 应使用支持并发的提交上下文或 stream；具体机制以所用版本的实际能力为准。

对照 H 的提交调用耗时与完成时延，并检查时间线：如果 H 在调用提交接口前或接口内部等待明显增加，应先分析锁、CPU 调度、提交队列及同步依赖。若 H/P 实际没有重叠，就不能解释为并发访问路径中的竞争。

### 7.2 MTE

区分两个阶段：一是 H kernel 尚未启动，二是 H kernel 已启动但读取完成变慢。前者主要涉及调度和执行资源占用，后者才支持进一步分析 kernel 内访存路径；kernel 内变慢仍可能有其他原因。

在主实验之外增加后台 block 数敏感性测试，从少量 block 开始逐步增加，并记录 H kernel 的启动等待和执行时长。K 与 block 数是两个独立参数，测试其中一个时应固定另一个；若实现无法独立控制，必须记录耦合关系。

kernel 总时长不能直接等同于 MTE 读取耗时。应尽量通过内部计时或可用 profiling 区分读取、同步和其他计算；如果无法区分，只报告 kernel 层指标及其限制。

## 8 跨服务器扩展

第二阶段将服务器 A 的一个 NPU 设为 D0，服务器 B 的一个 NPU 设为 D1，二者必须位于同一 A3 超节点内，并重新验证指定后端直接访问能力。

重复 E1 至 E4，保持请求大小、K、地址序列、工作集、随机种子、准入策略、采样口径和后端一致。MTE 的 block 数及每 block 工作量也应保持一致。

跨服务器测试使用其自身 E1 基线计算尾时延放大，同时展示同机与跨机的绝对时延和吞吐。记录服务器及设备差异；若无法使用相同型号或相同配置，应将差异作为解释限制。

若跨服务器路径需要更换后端或发生主机中转，则单独列为另一组实验，不能将性能差异全部归因于跨服务器访问路径。

## 10 结论判定与汇报措辞

| 观察结果 | 可以支持的判断 | 仍需补充的证据 |
| --- | --- | --- |
| H/P 重叠时，H 尾时延稳定高于基线 | 当前配置存在负载干扰 | 干扰发生于哪个具体资源 |
| P 吞吐趋稳而 H p99 继续恶化 | 继续增加逻辑积压的收益有限 | 硬件槽位或缓冲是否耗尽 |
| 匹配字节负载后，小块 P 干扰更强 | 请求数量、访问方式或控制开销值得追查 | 事务拆分和具体瓶颈的区分 |
| 固定工作量下限流改善 H p99 | 准入控制在该配置下有效 | 收益能否覆盖其他工作负载与实现开销 |
| MTE 的 H 启动等待显著增加 | 执行资源或调度干扰需要优先分析 | H 启动后的访存是否也受影响 |

“明显上升”“吞吐趋稳”等判定应结合重复轮次波动及实际业务可接受范围，提前约定阈值，避免事后只挑有利数据。没有统一阈值时，报告连续数值和波动范围。

若观察到稳定现象，可在汇报中使用：

> 在 A3 超节点的指定访存路径上，并发后台读取使关键读取尾时延上升。通过限制后台逻辑在途数量或调整准入顺序，可在一定吞吐代价下改善关键读取时延，表明共享访存资源协调存在优化空间。

具体报告时应补充后端、拓扑、负载、改善幅度和代价。只有完成硬件指标、profiling 或仿真验证后，才能进一步讨论特定请求资源耗尽及 CMU 对该资源的作用。

## 11 执行顺序与待确定参数

推荐顺序为：设备映射与路径验证 → 正确性与重叠预检 → E1 → 连续地址的 E2 预试验 → 完整 E2 → E3 → E4 → MTE 调度排查 → 同超节点跨服务器复测。

正式测试前填写并冻结以下参数：

- [ ] D0/D1 设备、rank、物理端点及服务器映射。
- [ ] 实际后端接口、并发能力、完成语义及路径验证结果。
- [ ] H/P 工作集、对齐、连续步长、离散地址种子。
- [ ] 一个逻辑请求的定义、K 的实现及实际在途统计方法。
- [ ] H 间隔 G、提交上下文、线程与 CPU 亲和性。
- [ ] MTE 后台 block 数、每 block 工作量及 K 与 kernel 的关系。
- [ ] 预热、采样时长、样本数、重复轮次及配置随机化顺序。
- [ ] E3 的累计字节量 B、共同目标字节率 R、突发预算及在途上限。
- [ ] E4 的 K_high、K_low、固定 H/P 数量与准入策略实现。
- [ ] 计时与完成检测方法、统计算法、异常处理和有效轮次标准。
